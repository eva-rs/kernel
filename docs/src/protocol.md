# Протокол модулей

Модуль — отдельный процесс, который говорит с soul по симметричному мультиплексированному RPC поверх msgpack; кто из них звонит, задаёт вид модуля. Глава описывает провод для автора модуля на любом языке; на Rust то же самое делает [`eva-sdk`](sdk.md). Каталог операций — в [Библиотечном API](api.md), значения таймингов и лимитов — ключи секции `modules` из [Конфигурации](config.md#транспорт); ниже везде указаны их умолчания.

## Транспорты

Кто звонит, задаёт вид модуля:

| Вид | Соединение | Транспорты | Аутентификация |
|---|---|---|---|
| сервис (мост мессенджера, MCP) | soul → модуль | uds, tcp — оба под Noise | общий PSK |
| клиент (телефон, TUI) | модуль → soul | uds, ws, wss; http, https — [HTTP-мост](#http-мост-json-rpc) | токен в `hello`; у моста — `Authorization: Bearer` |

Сервис не знает адреса soul — только слушает. Клиенты за NAT и приходят-уходят, поэтому звонят сами. Транспорты кадров несут одинаковые кадры; HTTP-мост несёт те же операции в конверте JSON-RPC без сессии.

### Слушатель soul (клиенты)

| Транспорт | Слушатель soul | Адрес у модуля | Кадрирование |
|---|---|---|---|
| Unix-сокет | `{uds: <путь>}` | `uds:///run/eva-soul/modules.sock` (или `unix://`) | `u32` big-endian длина, затем msgpack-кадр |
| WebSocket | `{ws: <addr:port>}` | `ws://host:port/v1/modules` | один binary-message — один кадр |
| WebSocket + TLS | `{wss: <addr:port>, tls: {cert, key}}` | `wss://host:port/v1/modules` | то же поверх TLS |
| HTTP | `{http: <addr:port>, cors?: [origin]}` | `http://host:port/v1/rpc` | конверт JSON-RPC 2.0 в теле `POST`, без кадров и сессии |
| HTTPS | `{https: <addr:port>, tls: {cert, key}, cors?}` | `https://host:port/v1/rpc` | то же поверх TLS |

- WebSocket-Upgrade принимается только на пути `/v1/modules`, иначе HTTP 404. У клиента SDK пустой путь дополняется до `/v1/modules`.
- Text-message в WebSocket — нарушение протокола, соединение закрывается. Ping/pong WebSocket-уровня протокол не использует — у него свой `ping`.
- Кадр больше `max_frame` (16 MiB) закрывает соединение с `invalid_params`.
- Закрытие с причиной: перед закрытием сокета пир шлёт уведомление `close` (см. ниже). WebSocket дополнительно передаёт причину close-кадром: код 1008 и текст до 123 байт; штатное закрытие — код 1000 без текста. У uds и Noise close-кадра нет — причину несёт только `close`.

### HTTP-мост (JSON-RPC)

Для клиентов без постоянного соединения (скрипт, `curl`, веб-страница): те же операции и те же права, что по кадрам, но потоков, загрузок и событий нет — за ними ws.

- `POST /v1/rpc`, тело — объект JSON-RPC 2.0 `{"jsonrpc": "2.0", "id": …, "method": "<ns>.<op>", "params": {…}}`; `params` — ровно `Args` операции, как `params` кадра `request`; без `params` — `Args` по умолчанию. `id` — число, строка или `null`, возвращается как пришёл; запрос без `id` — уведомление: исполняется, ответа не получает.
- Кодек: `Content-Type: application/json` или `application/msgpack` задаёт кодек запроса (иначе `415`), `Accept` — кодек ответа (по умолчанию — кодек запроса). msgpack-конверт — карта с теми же ключами; типы в теле — как в [кодировке](#кодировка) провода, в JSON байты — массив чисел, `Timestamp` — строка.
- Токен — `Authorization: Bearer <token>`: проверяется как `hello.token` (конфиг `modules.tokens` и выданные `modules.token_issue`, отозванный не годится, отказ после паузы 250 мс), нет или не принят — `401` с `WWW-Authenticate: Bearer`. Каждый запрос — одноразовая сессия клиента: строки `modules` она не создаёт, живую сессию того же клиента не вытесняет, окна идемпотентности и `resume` у неё нет.
- Массив запросов — batch до `max_batch` (64): исполняется по порядку, ответ — массив ответов в том же порядке без ответов на уведомления; пустой или слишком длинный batch отвергается целиком одной ошибкой с `id: null`. Нечего ответить — `204 No Content`.
- Ответ: `{"jsonrpc": "2.0", "id": …, "result": <Ok>}` либо `{"jsonrpc": "2.0", "id": …, "error": {"code", "message", "data"}}`. `error.code` — стандартный JSON-RPC (`-32700` тело не разобрано, `-32600` не запрос, `-32601` метода нет, `-32602` `invalid_params`, `-32603` `internal`) или свой на [код провода](#коды-и-данные-ошибок): `-32001` `unauthorized`, `-32003` `forbidden`, `-32004` `not_found`, `-32008` `timeout`, `-32009` `conflict`, `-32010` `cancelled`, `-32011` `unavailable`, `-32012` `proto_version`, `-32013` `quota`. `error.message` — текст ошибки, `error.data` — `{"code": "<код провода>", "retry_after"?: длительность, "error"?: <Generic<Err>>}`, где `error` — тот же объект, что `data` в `RpcError` кадра (`{"forbidden": "…"}`, `{"not_found": {"surface": "x"}}`).
- Операция-поток или загрузка (`turns.attach`, `blobs.get`, `blobs.put`) отвечает `-32601` с текстом `use ws`.
- HTTP-статус не `200` только когда тело до операции не дошло: `415` кодек, `413` тело больше `max_frame`, `401` токен, `403` чужой `Origin`, `404`/`405` не `POST /v1/rpc`. Ошибки операций и разбора — `200` с объектом `error`.
- CORS: без `cors` слушатель на loopback-адресе отвечает любому `Origin`, слушатель на другом адресе — никакому; `cors: [origin, …]` — только перечисленным (`scheme://host[:port]`, без учёта регистра). Preflight `OPTIONS /v1/rpc` разрешает `POST` с заголовками `Authorization`, `Content-Type`, `Accept`. Запрос без `Origin` (не браузер) списка не касается.
- До первого принятого токена соединение занимает место в том же лимите, что и ws до `hello` (64 соединений, 8 на сеть); заголовки запроса приходят за `handshake_timeout`, иначе соединение закрывается.

```sh
curl -s http://127.0.0.1:7080/v1/rpc \
  -H 'Authorization: Bearer <token>' -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"surfaces.get","params":{"surface":"local"}}'
```

### Сервисное соединение (Noise)

Сервис слушает `{uds: <путь>}` или `{tcp: <ip:port>}`; soul набирает его по адресу `uds:///<абсолютный путь>` или `tcp://<host>:<port>` (`host` резолвится на каждой попытке, TCP — с `nodelay`).

- Noise `Noise_NNpsk0_25519_ChaChaPoly_BLAKE2s`: soul — initiator, модуль — responder. Handshake — два сообщения с пустым payload: `→ psk, e`, `← e, ee`.
- PSK = HKDF-SHA256(ikm = секрет без хвостовых `\n`/`\r`, без salt, info = `eva-module psk v1`) → 32 байта. Секрет — высокой энтропии: NNpsk0 с угадываемым секретом подбирается офлайн по перехваченному handshake.
- Сообщение Noise на проводе — `u16` big-endian длина и шифротекст до 65535 байт (16 из них — тег AEAD), открытого текста в сообщении — до 65519 байт. Внутри расшифрованного потока — кадрирование uds (`u32` длина + msgpack-кадр); кадр длиннее сообщения идёт несколькими.
- Чужой PSK: модуль не расшифрует первое сообщение и закрывает сокет без ответа — soul видит обрыв.
- Noise, `hello` и `welcome` укладываются в один `handshake_timeout` от accept; сокет, не уложившийся, модуль закрывает. До конца Noise модуль держит не больше 64 соединений и 8 из одной сети (IPv4 — адрес, IPv6 — /64): сверх лимита новичок вытесняет старейшее, ещё не доказавшее ключ.

## Кодировка

Всё — msgpack **с именами полей** (карты, не позиционные массивы). Позиционная форма ломает разбор untagged-типов и пропуск незнакомых полей, поэтому другой нет.

| Что | Форма на проводе |
|---|---|
| Структура | карта `{имя_поля: значение}`; опциональное поле — `nil` или отсутствует |
| Enum | имена вариантов в `snake_case`, внешний тег: `"continue"` для варианта без данных, `{"cancel": {"reason": "…"}}` для варианта с данными |
| `Bytes` | msgpack `bin` |
| `Timestamp` | `u64` — наносекунды Unix-эпохи |
| `Date` | `u16` — дни от Unix-эпохи |
| Длительность | строка humantime: `"15s"`, `"1500ms"`, `"10m"` |
| Версия протокола | строка `"MAJOR.MINOR"` |
| id | целочисленные — число (на вход можно и `"42"`, `"c42"`), строковые — строка ([Идентификаторы](api.md#идентификаторы)) |

Разбор двухшаговый: `params`, `result`, `item` и `data` кадра — **`bin` с отдельным msgpack-документом** внутри, а не вложенная карта. Получатель сначала разбирает кадр, потом payload по методу. Незнакомый payload роняет только свой вызов, а не соединение.

## Кадры

Кадр — карта с одним ключом, имя которого — вид кадра:

| Вид | Поля | Смысл |
|---|---|---|
| `request` | `id: u64`, `method: str`, `params: bin` | Вызов; шлют оба пира |
| `response` | `id`, `result: bin?`, `error: RpcError?` | Ответ на не-потоковый вызов: ровно одно из `result`/`error` |
| `notify` | `method`, `params: bin` | Сообщение без ответа |
| `stream_item` | `id`, `seq: u64`, `item: bin` | Элемент потока на `request.id`; `seq` с 0 без дыр |
| `stream_heartbeat` | `id` | Поток или долгий вызов жив; `seq` не занимает |
| `stream_end` | `id`, `error: RpcError?` | Конец потока; `response` потоку не шлётся |
| `cancel` | `id` | Просьба прекратить вызов |

```text
{"request": {"id": 1, "method": "surfaces.get", "params": bin(msgpack {"surface": "x"})}}
{"response": {"id": 1, "result": bin(msgpack {"surface": {...}}), "error": nil}}
```

Незнакомый вид кадра получатель пропускает. Нераспознаваемый msgpack закрывает соединение с `invalid_params` («malformed frame»).

### Идентификаторы запросов

- `id` уникален в пространстве отправителя в пределах сессии. Модуль (сторона `hello`, кто бы ни звонил) нумерует с 0, soul — с 2^63, поэтому пространства не пересекаются: `stream_item`, `stream_heartbeat`, `stream_end` и `cancel` не несут направления и относятся к `id` того запроса, которому принадлежат, чей бы он ни был.
- `response` всегда отвечает на чужой `id`.
- Повтор `id`, который ещё обслуживается, игнорируется.
- После реконнекта с `resume` модуль продолжает прежний счётчик: новый запрос со старым `id` попал бы в окно идемпотентности ([ниже](#идемпотентность)).

## Handshake

```mermaid
sequenceDiagram
  participant M as модуль
  participant K as soul
  alt клиент
    M->>K: транспорт (TLS, Upgrade)
  else сервис
    K->>M: connect, Noise (→ psk, e / ← e, ee)
  end
  M->>K: request hello {version, proto_version, token?, capabilities, resume?}
  Note over K: токен клиента или набранная запись → id модуля и kind,<br/>проверка capabilities,<br/>вытеснение прежней сессии
  K-->>M: response welcome {session_id, module, kind, ...}
  M->>K: request surfaces.create {...}
  K-->>M: response {...}
```

Кто бы ни звонил, первый кадр шлёт модуль — `request` с методом `hello`; любой другой первый кадр — `invalid_params` и закрытие. Всё до `welcome` укладывается в `handshake_timeout` (10 s): у клиента — TLS, Upgrade и `hello` от accept, у сервиса — connect, Noise и `hello` от connect со стороны soul.

### `hello`

| Поле | Тип | Смысл |
|---|---|---|
| `version` | str | Версия модуля, видна в `modules.list` |
| `proto_version` | `"MAJOR.MINOR"` | Версия протокола модуля; текущая — `0.1` |
| `token` | str? | Секрет клиента; сервис, до которого дозвонился soul, его не шлёт |
| `capabilities` | карта | Что модуль умеет ([Capabilities](#capabilities)); отсутствует — ничего |
| `resume` | `{session_id}`? | Тот же процесс, что прошлая сессия: продолжить окно идемпотентности |

Имени модуля в `hello` нет. Идентичность сервиса — запись, которую набрал soul: Noise уже доказал обеим сторонам общий PSK. Идентичность клиента — **токен**. Soul ищет его среди `modules.tokens` конфига (ключ записи — id модуля) и среди выданных операцией `modules.token_issue`; запись конфига (токен или сервис) сильнее выданного для того же имени. Токен есть только у клиента: сервис живёт в реестре `modules.services` / `modules.add` ([Конфигурация](config.md#сервисы-modulesservices)). Id — одно пространство имён у сервисов и клиентов; `soul`, `system`, `local` зарезервированы: такую запись конфига soul не принимает при старте, `token_issue` и `modules.add` отвечают `invalid_params`. Имя модуля — `[a-z][a-z0-9_-]{0,63}`.

### `welcome`

| Поле | Тип | Смысл |
|---|---|---|
| `session_id` | str (uuid v7) | Id сессии; его предъявляют в `hello.resume` |
| `module` | str | Id модуля — ключ записи реестра (сервис) или токена (клиент). Скоуп `fs`/`sqlite`/`kv` и значение `surface.module` у созданных им surface |
| `soul_version` | str | Версия soul |
| `proto_version` | `"MAJOR.MINOR"` | Версия протокола soul |
| `kind` | `"client"` \| `"service"` | Вид соединения — набрал ли его soul или оно пришло с токеном: по нему модуль знает свои права ([Безопасность](security.md#вызывающие-и-их-права)) |
| `services` | [str] | Неймспейсы операций, которые обслуживает soul по RPC |
| `tool_ids` | {путь тула: id} | Постоянные ID зарегистрированных инструментов; сохраняются после реконнекта |
| `models_accepted` | [str] | Принятые модели провайдера модуля |
| `warnings` | [`{code, subject, message}`] | Отклонённые части `hello`; сессия при этом жива |
| `resumed` | bool | `hello.resume` продолжил окно идемпотентности прошлой сессии |

### Отказы

Отказ приходит `response` на `hello` с `error` (или уведомлением `close`, если запроса не было), затем соединение закрывается.

| Причина | Код |
|---|---|
| `hello` не пришёл за `handshake_timeout` | `timeout` |
| Первый кадр — не `request hello`, `params` не разбираются | `invalid_params` |
| Кадр `hello` клиента больше `max_hello` (4 MiB, не больше `max_frame`) — переподключаться бессмысленно; `hello` сервиса держит лишь `max_frame` | `invalid_params` |
| `hello` сервиса несёт `token` | `invalid_params` |
| MAJOR `proto_version` не равен текущему | `proto_version` |
| Токен клиента не найден, пуст, отсутствует или отозван; ответ — после паузы 250 ms | `unauthorized` |
| Токен отозван или сервис убран `modules.remove` во время handshake | `unauthorized` (без паузы) |

До `welcome` слушатель клиентов держит не больше 64 соединений всего и 8 из одной сети (IPv4-адрес или IPv6 /64). Сверх лимита новичок вытесняет старейшее соединение, ещё не приславшее `hello`. Сервиса, до которого дозвонился soul, эти лимиты не касаются: он уже доказал PSK.

### Сессия модуля

- **Одна сессия на id.** Новая сессия того же id вытесняет прежнюю: та закрывается с кодом `conflict` («superseded»). У клиента это новый `hello` с тем же токеном — переподключаться после вытеснения не надо, это драка двух процессов за один токен. У сервиса на SDK это новое соединение от soul после `welcome` на нём (рестарт soul): прежнее соединение закрывается, `Soul` модуля идёт уже через новое.
- **Отзыв и ротация.** `modules.token_revoke` и выдача нового токена закрывают сессии клиента с `unauthorized`; токен конфига они не трогают.
- **Удаление сервиса.** `modules.remove` закрывает сессию сервиса с `unauthorized` («module removed») и гасит его дозвон; запись `modules.services` снимается только правкой конфига.
- **Дозвон.** Soul заново набирает оборванную сессию сервиса с паузой 1s…60s ([Конфигурация](config.md#сервисы-modulesservices)); сервис переподключаться не пытается.
- **Остановка soul** сначала гасит дозвон, затем закрывает сессии с `unavailable` («soul is shutting down») — клиенту это повод переподключиться, сервису — ждать нового звонка.
- Закрытая сессия переводит модуль в `offline`; модуль, молчащий дольше `modules.offline_forget` (7 дней), становится `forgotten`.

## Capabilities

Секция отсутствует — capability не объявлена; пустой список — ровно ноль элементов. Soul пропускает незнакомый ключ `capabilities` и сообщает о нём в `welcome.warnings` (`invalid_params`, `subject: capabilities.<ключ>`).

| Ключ | Форма | Что делает soul |
|---|---|---|
| `provider` | `{decl, models}` | Принимает и регистрирует модели (запасной вход провайдера) |
| `tools` | `{groups: [{path, about}], tools: [ToolDecl]}` | Проверяет, регистрирует и вызывает через `tools.call` |
| `events` | `{subscriptions: [топик]}` | Рассылает события |
| `hooks` | `{points: [точка], timeout?, fail_mode}` | Вызывает объявленные хуки в турах |
| `ask` | bool | Учитывает возможность показать вопросы и запросы разрешений |

Surface — не capability, а сущность soul: модуль создаёт её операцией `surfaces.create`, soul запоминает создателя. Обслуживает surface живая сессия её модуля-создателя, встроенную `local` — каждая сессия `client`; `system` не обслуживает никто. После реконнекта регистрировать surface заново не нужно.

### `ask`

Модуль умеет рисовать кнопки pending-запросов (вопрос, разрешение) в чатах surface, которые обслуживает. Soul считает чат способным на кнопки, если хоть одна обслуживающая его surface живая сессия объявила `ask`.

### `tools`

`ToolDecl`: `path` (через точку, не меньше двух сегментов `[a-z][a-z0-9_]*`; каноничное имя — точки заменены на `_`, не длиннее 64 символов), `description` (одна строка), `input` (JSON Schema draft 2020-12), флаги `master_only`, `trusted_only`, `ends_turn`, `parallel_safe`, `waits_on_cancel`, `idempotent`, `needs: [need]`, `result: windowed|uncapped`, `timeout?`. Группа: `path` (от одного сегмента) и `about` (одна строка). Невалидный тул или группа отклоняются по одному, с причиной в `warnings`.

Если флаги не заданы, `idempotent` и `parallel_safe` равны `true`, остальные — `false`; SDK использует те же дефолты. Неидемпотентные операции явно передают `idempotent: false`. Этот флаг пока декларативный и не включает автоматические повторы. `parallel_safe: false` сохраняет порядок вызовов внутри одного ответа модели, но не сериализует вызовы из разных туров.

Вызов — поток `tools.call` от soul:

| Шаг | Форма |
|---|---|
| `params` | `{call_id, tool_id?, canonical, input, ctx}`; `call_id` — ключ дедупа повтора после реконнекта |
| элементы | `{"progress": {"text", "message"?}}`* затем один `{"result": {"content", "is_error"}}` |
| `is_error: true` | данные для модели, тур продолжается |
| `stream_end{error}` | фатальная ошибка, тур падает |

`progress.message` — необязательный `LocalizedText`: `{domain, revision, message: {id, context?, plural?, count?, args}, translations}`. `text` всегда содержит готовый fallback, `translations` — отображение locale в шаблон только текущей строки (plural-форма уже выбрана по `count`). Получатель подставляет `args`, ищет регион → язык → оригинал. Это же поле доступно в `ItemDelta::Progress`; старые отправители и получатели продолжают работать с одним `text`. Soul скрабит параметры и переводы вместе с текстом, при обнаружении секрета удаляет метаданные. Подробнее — [Локализация прогресса](sdk.md#локализация-прогресса).

Незавершённый `tools.call` ждёт реконнекта модуля `modules.call_reconnect_grace` (30 s).

### `events`

`notify events.publish` с `params` `{topic, seq, at, payload}`. В msgpack `topic` обязан идти раньше `payload`: форма `payload` зависит от топика. `seq` — счётчик сессии с 0; порядок — порядок публикации; реплея после реконнекта нет. Сервис получает только события своих surface; события без surface — только клиенты.

| Топик | `payload` |
|---|---|
| `chat.created`, `chat.deleted`, `chat.restored` | `{chat, surface, external_id?}` |
| `chat.purged` | `{ids}` — по событию на surface |
| `memory.changed` | `{ids, op}`; без surface |
| `module.connected`, `module.disconnected` | `{module}`; без surface |
| `turn.started`, `turn.finished` | `{turn_id, chat, surface, actor, run_id?, outcome?}` |
| `tool.called` | `{turn_id, chat, tool_id?, canonical, is_error, duration}` |
| `notify` | `{subject, chat_id, source_chat?}`; только клиентам |
| `cron.fired` | `{job, run_id, chat}` |
| `sleep.phase` | `{phase, run_id, state}` |

### `hooks`

Точки: `before_turn` (после актора, до первого шага), `before_tool` (после проверки видимости, до исполнения), `after_tool` (до скраба секретов, окна и записи в лог; патч — `result`). У `before_turn` и `before_tool` патчить нечего: реплика и вызов уже в логе, и `patch` там считается отказом хука по `fail_mode`. Хуки идут цепочкой по модулям в порядке имён; сервис получает только туры чатов своих surface, клиент — любые, модуль запасного входа `provider` — никакие. Soul зовёт только объявленные точки: `request hooks.<point>` с входом точки, ответ — решение:

```text
"continue" | {"cancel": {"reason": "…"}} | {"patch": {"payload": …}}
```

Патч передаётся следующему хуку цепочки. `timeout` модуля обрезается до `modules.hooks.timeout` (2 s). `fail_mode` — что делать при таймауте, ошибке, незнакомом решении или offline-модуле: `open` (по умолчанию) — продолжить, `closed` — отменить.

### `provider`

Запасной вход провайдера инференса. Принимается, только если модуль назван в `llm.providers` с `kind: module`; иначе секция отбрасывается с предупреждением `forbidden`, сессия живёт. Методы soul: `provider.generate` (поток `GenItem`), `provider.embed`, `provider.count_tokens` (`{tokens}`); ошибка несёт в `data` msgpack `ProviderError`. Подробно — [Провайдеры → kind: module](providers.md#kind-module).

## Методы

| Метод | Кто зовёт | Вид | Смысл |
|---|---|---|---|
| `hello` | модуль | request | Первый кадр сессии |
| `ping` | оба | notify, `params` — `{}` | Соединение живо |
| `close` | оба | notify, `params` — `RpcError` | Причина закрытия; последний кадр перед закрытием сокета |
| `<namespace>.<op>` | модуль | request | Операция библиотеки: `surfaces.create`, `chats.move`, `kv.set`… ([список](api.md#операции)) |
| `tools.call` | soul | request → поток | Вызов тула модуля |
| `hooks.<point>` | soul | request | Хук тура |
| `events.publish` | soul | notify | Событие по подписке |
| `provider.generate` | soul | request → поток | Генерация |
| `provider.embed`, `provider.count_tokens` | soul | request | Эмбеддинги, подсчёт токенов |

Имена — `snake_case`, неймспейс и операция через точку. Незнакомый метод — `unknown_method`; модуль отвечает так же на вызов, который не объявлял. Операции `blobs.get` и `turns.attach` отвечают потоком, `blobs.put` — загрузка.

## Коды и данные ошибок

`RpcError`: `{code, message, data?: bin, retry_after?: длительность}`.

- `data` есть у ошибок операции — msgpack её `Generic<Err>`: либо `Aux` (`{"forbidden": "…"}`), либо собственная ошибка операции (`{"not_found": {"surface": "x"}}`). Получатель пробует `Aux`, затем `Err` операции. У ошибок провайдера `data` — `ProviderError`. Без `data` — ошибка транспорта.
- `retry_after` — только у квот и временной недоступности провайдера.
- Код решает сторона, знающая причину; по тексту его не угадывают. Код новее пира читается как `unknown`.

| Код | Когда |
|---|---|
| `unknown_method` | Метод неизвестен |
| `invalid_params` | `params` не разобраны или не прошли валидацию; нарушение протокола: кадр больше `max_frame`, мусор вместо кадра, `seq` не по порядку, чанк больше `blob_chunk`, `id` уже занят другим методом |
| `unauthorized` | Токен не принят, отозван или ротирован |
| `forbidden` | Caller не вправе ([Безопасность](security.md)) |
| `not_found` | Объекта нет |
| `conflict` | Состояние изменилось; сессия вытеснена; ответ мутации не сохранён в окне идемпотентности |
| `timeout` | Нет `hello`, ответа, кадров потока или любых байт дольше срока |
| `cancelled` | Вызов отменён |
| `unavailable` | Компонент недоступен, операция невозможна в текущем состоянии или соединение закрыто |
| `proto_version` | MAJOR версии протокола не поддерживается |
| `quota` | Лимит: `max_inflight`, `max_streams`, буфер потока, квоты песочницы |
| `internal` | Сбой soul или базы |

`Aux` → код: `Forbidden` → `forbidden`, `NotFound` → `not_found`, `Invalid` → `invalid_params`, `Conflict` → `conflict`, `Quota` → `quota`, `Unavailable` → `unavailable`, `Db`/`Internal` → `internal`. Обратно без `data`: `timeout`/`cancelled`/`unavailable` → `Unavailable`; `unknown_method`/`proto_version`/`invalid_params` → `Invalid`; `unauthorized`/`forbidden` → `Forbidden`; прочие — одноимённые, `unknown` → `Internal`.

## Потоки

```mermaid
sequenceDiagram
  participant C as вызывающий
  participant S as обработчик
  C->>S: request {id: 7, method: blobs.get}
  S-->>C: stream_heartbeat {id: 7}
  S-->>C: stream_item {id: 7, seq: 0}
  S-->>C: stream_item {id: 7, seq: 1}
  S-->>C: stream_heartbeat {id: 7}
  S-->>C: stream_end {id: 7, error: nil}
```

- **Открытие.** Сразу после открытия обработчик шлёт `stream_heartbeat` — «открыт». Вызывающий ждёт первый кадр потока `request_timeout` (60 s); `stream_end{error}` первым кадром — отказ до первого элемента.
- **Элементы.** `seq` с 0 без дыр; пропуск — `invalid_params`, поток рвётся. Ошибка внутри потока — `stream_end{error}`, она последняя.
- **Heartbeat.** Каждые `ping_interval` (15 s) без элементов обработчик шлёт `stream_heartbeat`. Поток без кадров дольше `stream_idle_timeout` (2 min) вызывающий отменяет (`cancel`) и получает `timeout`.
- **Долгие не-потоковые вызовы** обработчик тоже подтверждает `stream_heartbeat` на `id` запроса раз в `ping_interval`; `request_timeout` — срок тишины, heartbeat его продлевает.
- **Отмена.** `cancel{id}` — обработчик отвечает `stream_end` (поток) или `response` (вызов, загрузка) с `cancelled`. Мутирующая операция от `cancel` не прерывается: вызывающий сразу получает `cancelled`, а итог операции ложится в окно идемпотентности.
- **Обратное давление.** У получателя на каждый поток буфер в `stream_buffer` (64) элементов; читатель сокета никого не ждёт. Переполнение рвёт только этот поток: получатель видит `quota` («stream buffer overflow») и шлёт отправителю `cancel`. Уведомления обрабатываются по одному в порядке прихода; переполненная очередь уведомлений теряет новые.
- **Лимиты сессии.** Одновременных не-потоковых запросов и загрузок — `max_inflight` (64), потоков — `max_streams` (256); сверх — сразу `quota`. Ответ, не влезший в `max_frame`, заменяется `invalid_params`; если неотправленных ответов больше 4 × `max_frame` (пир не читает сокет), новый ответ заменяется `quota`.
- **Данные одного ответа или элемента** — `max_frame` минус 256 байт конверта.

### Лента тура

`turns.attach` передаёт `TurnItem {seq, sub, replayed, event}`. Курсор `seq`
принадлежит журналу чата; он отличается от транспортного номера `stream_item.seq`.
Клиент сохраняет курсор и после реконнекта открывает подписку заново с `since_seq`.
Повторившийся исторический item применяется по его ID, без второго пузыря.

`ItemStarted` и `ItemDelta` показывают текущий вывод. `ItemCompleted` содержит
авторитетный item и `replaces` — ID живого item, который нужно заменить на месте.
`UserMessage.external_id` связывает реплику с отправленным сообщением поверхности.
Вложения представлены отдельно: `ItemBody::Image` и `ItemBody::File`, оба с blob ID
и ссылкой `eva-blob://<id>`; байты выдаёт `blobs.get`. `TurnDone` содержит `outcome`
и текст `error` при неудаче. Детали — в главе [Туры](turns.md).

### Загрузка

`blobs.put` — поток от вызывающего: `request` с `put::Meta` (метаданные тела), затем `stream_item` на тот же `id`, у каждого `item` — msgpack `bin` чанка, затем `stream_end` и один `response` от soul. Чанк не больше `blob_chunk` (1 MiB); крупнее — `invalid_params`. Непрочитанные чанки всех загрузок сессии занимают не больше одного буфера `stream_buffer` чанков; сверх — `quota`. Ранний `response` от soul (например, отказ по правам) означает, что остаток тела можно не слать. Обрыв источника — `stream_end{error}`.

## Идемпотентность

Soul помнит ответ **мутирующей** операции (вид `mut` в [каталоге](api.md#операции)) по `(session_id, request.id)`:

- повтор того же `id` с тем же методом отдаёт сохранённый ответ, а не исполняет операцию снова; если исходный вызов ещё идёт — ждёт его итога;
- тот же `id` с другим методом — `invalid_params`;
- не хранятся итоги с кодами `internal`, `unavailable`, `timeout`, `cancelled` — такой повтор исполняется заново;
- ответ больше 64 KiB не хранится, но запись о исполнении остаётся: повтор получит `conflict` («request already executed; its response is not retained»), а не второй эффект. Так же при вытеснении итогов по объёму: 16 MiB на окно, 64 MiB на все окна soul;
- окно живёт `idempotency_window` (10 min) после конца сессии; сверх 16 384 завершённых записей в окне старейшие забываются.

Окно переносится на новую сессию через `hello.resume{session_id}`, если `session_id` — прошлая сессия того же модуля. Тогда `welcome.resumed = true`, и оборванную мутацию безопасно повторить тем же `id`. `resumed = false` (например, после рестарта soul или истечения окна) значит, что повтор тем же `id` исполнит операцию снова. Чтения не кэшируются: их просто повторяют.

## Ping и таймауты

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `handshake_timeout` | 10 s | TLS, Upgrade и `hello` |
| `ping_interval` | 15 s | Период `notify ping` и heartbeat долгих вызовов |
| `ping_timeout` | 45 s | Ни одного байта от пира дольше — закрытие с `timeout` («ping timeout») |
| `request_timeout` | 60 s | Тишина до ответа на не-потоковый вызов; первый кадр потока |
| `stream_idle_timeout` | 2 min | Поток без кадров |

Оба пира шлют `ping` сами; отвечать на него не нужно. Тишина считается по байтам сокета, а не по кадрам: крупный кадр на медленной линии соединение не роняет. Модуль должен использовать те же значения, что и soul, — у SDK это те же ключи в секции `module`.

## Совместимость

- Версия протокола — `MAJOR.MINOR` крейта `eva-protocol`. MINOR только добавляет поля, варианты и методы; MAJOR ломает.
- Soul принимает только текущий MAJOR.
- Незнакомые поля структур получатель пропускает — в кадрах, `hello`, `welcome`, payload.
- Enum'ы, которые пир получает от пира, терпят незнакомый вариант: вид кадра, код ошибки, топик и событие, точка хука, решение хука (читается как отказ хука по `fail_mode`), элемент `tools.call`, `fail_mode` (читается как `open`) и другие перечисления ответов. Незнакомый вариант становится `unknown` или ближайшим безопасным вариантом, соединение живо.
- `Args` запросов строгие: незнакомый вариант enum'а в аргументах — `invalid_params`.
- Незнакомый ключ `capabilities` — предупреждение в `welcome.warnings`.
